# Demo auth work log — 2026-10-08

Owner: backend. Scope: `lib/auth.ts`, `.env.example`, this document.
(`lib/session.ts` and `lib/auth-types.d.ts` were reviewed and required no
change; no other files were touched.)

## Requirement

Allow an opt-in, email-only demo sign-in so a public demo can be used without
real Google accounts, while keeping the real authorization model intact:

- professor = the **exact** `PROFESSOR_EMAIL` (never inferred from a domain);
- student = an `@iiitdm.ac.in` address that is **present in the roster**;
- any **non-empty** password is accepted and the password is never verified,
  hashed, logged, or stored.

## What changed

### `lib/auth.ts`

- Added a third, **conditional** provider: `demo-credentials`
  (`next-auth/providers/credentials`, id `demo-credentials`).
  It is pushed into the provider list **only** when
  `DEMO_AUTH_ENABLED === 'true'`. When the flag is unset the provider does not
  exist at all, so there is no demo attack surface by default.
- `isDemoAuthEnabled()` treats only an explicit `true` as enabled. Unset,
  empty, `false`, `1`, etc. all mean **disabled**. There is no default enable.
- `authorize(credentials)`:
  - requires a non-empty `email` and a non-empty `password`
    (`password.length === 0` is rejected; the value is otherwise ignored);
  - resolves the identity with the **same rules as real sign-in** via
    `resolveDemoIdentity()`:
    - exact `PROFESSOR_EMAIL` -> admin;
    - `@iiitdm.ac.in` **and** `findStudentByEmail()` hit -> student;
    - everything else -> denied.
  - returns `{ id, email, name }` only. No password field is ever included.
- `signIn` callback: a dedicated branch for `demo-credentials` re-checks the
  env flag and re-applies `resolveDemoIdentity()` (defense in depth) instead of
  the Google `email_verified` check (which does not exist for credentials).
  The Google `google` / `google-professor` paths are unchanged.
- Role differentiation is unchanged and stays email-derived in the `jwt`
  callback: `isProfessorEmail(email) ? 'admin' : 'student'`. The demo flow does
  not get to declare its own role.

### `.env.example`

Added, disabled by default:

```
DEMO_AUTH_ENABLED=false
```

with a comment stating it is impersonation-grade, synthetic-data-only, never to
be enabled with real student data, that passwords are not stored/verified, and
that it grants no Google Calendar authorization.

## Security posture (explicit)

- **Opt-in only.** No default enable; absent flag => provider absent.
- **Synthetic data only.** With the flag on, anyone who knows (or guesses) a
  roster email can sign in as that student, and anyone can sign in as the
  professor by using the exact `PROFESSOR_EMAIL`. This is intentionally
  impersonation-prone and must never be enabled on a deployment holding real
  student data.
- **No password handling.** The password is only checked for non-emptiness; it
  is never verified, hashed, logged, or persisted. Sessions are stateless JWT.
- **Email credentials are not Google authorization.** The demo provider cannot
  mint, read, or extend a Google Calendar token. It only establishes an
  application session/role.

## Google Calendar after a credential login

The real `google-professor` OAuth provider is kept unchanged and remains the
only way to grant Calendar consent. After a professor signs in with demo
credentials:

- the `jwt` callback sees a non-`google-professor` provider and resolves
  `hasCalendar` from the encrypted `oauth_tokens` row
  (`hasProfessorRefreshToken()`), so an already-connected Calendar is
  recognized immediately;
- to connect for the first time (or re-consent), the professor still completes
  the `google-professor` flow; the refresh token is persisted AES-256-GCM
  encrypted server-side in `oauth_tokens` and never placed in the JWT.

`lib/session.ts` (`getSession`/`requireSession`/`requireAdmin`/`requireStudent`)
needed no change: role and `hasCalendar` already come from the JWT and work
identically for demo sessions.

## Verification performed

Clean `rm -rf .next && npm run build` succeeds; `npx tsc --noEmit` is clean.

Exercised against a locally built server (throwaway PostgreSQL 17 cluster,
schema applied, seeded synthetic student):

- `/api/auth/providers` with `DEMO_AUTH_ENABLED` unset -> only `google` and
  `google-professor`.
- `/api/auth/providers` with `DEMO_AUTH_ENABLED=true` -> additionally exposes
  `demo-credentials`.
- `POST /api/auth/callback/demo-credentials`:
  - `professor@iiitdm.ac.in` + non-empty password -> 200, session
    `role: "admin"`, `studentId: null`, `hasCalendar: false`.
  - seeded `student@iiitdm.ac.in` + non-empty password -> 200, session
    `role: "student"`, `studentId: 1`.
  - `ghost@iiitdm.ac.in` (domain OK, not in roster) -> 401.
  - `student@example.com` (wrong domain) -> 401.
  - empty password -> 401.
- With a pre-seeded encrypted `oauth_tokens` row for the professor, demo
  credential login yields session `hasCalendar: true`, proving an existing
  Google Calendar connection survives a credential login.

## Not done / caveats

- No UI was added (frontend is out of scope for this change). The
  `demo-credentials` provider is only reachable via the NextAuth endpoints /
  whatever demo UI is wired later.
- The live Google `google-professor` redirect + token exchange were not run
  here (no Google client); persistence and recognition were verified with a
  correctly encrypted synthetic token instead.
