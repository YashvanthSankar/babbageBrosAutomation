## Demo sign-in contract (frontend → backend)

The frontend sends only credentials; it never sends a role:

```
signIn("credentials", { email, password, redirect: false })
```

- Any nonempty password is accepted (demo). The exact message shown to users is
  **“Demo mode: any nonempty password; synthetic records only.”**
- Role (professor/admin vs student) must be resolved server-side from the account
  email (e.g. exact professor email → admin, roster student → student). The UI has
  no role toggle.
- On `result.error` the UI maps `CredentialsSignin`, `AccessDenied` and
  `Configuration` to plain-language messages instead of failing silently.
- This depends on a server-side `credentials` provider existing in `lib/auth.ts`
  (owned by the backend, not touched here). Until it exists, `signIn` cannot
  start and the form surfaces that honestly.

## Calendar consent (no pretending)

- Google Calendar remains a **separate** `google-professor` OAuth action, offered
  only inside the professor dashboard (the role is unknown on the landing).
- Status is derived from `session.user.hasCalendar`; when false the card explains
  students cannot book real slots and booking reports local-only availability.
- Students are never asked for Calendar scopes.
